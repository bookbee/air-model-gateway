What it is

One HTTP service through which every AIR service reaches a language or embedding model: POST /v1/generate for text (optionally structured JSON, optionally streamed) and POST /v1/embed for vectors. Callers choose a model class (local, auto, cloud) or a published embedding model (local-768-v1), never a model name. The gateway owns everything else: which models serve each class, failover, retries, circuit breakers, authentication, permissions, rate limits, budgets, cost accounting, caching and observability.

1 · System context

Who calls the gateway, and what it callsBig picture
  1. ConsumersFive AIR services, each with its own token and grants. They call it directly over HTTP; there is no shared SDK requirement.
  2. One APITwo model routes. /v1/capabilities tells a caller what its classes mean; health and readiness serve probes.
  3. Owner-managed configModels, chains, prices and grants are files in deploy/: an edit and a deploy, never a code release.
  4. Local modelsFree and private. local never leaves the network; auto tries local first.
  5. Cloud modelsBilled per token, priced from deploy/pricing.yaml. Cross-vendor chains survive one vendor's outage.
  6. Redis, optionalShares cache, rate limits and spend across replicas. Without it, or when it fails, each replica keeps state in memory.
  7. ObservabilityPrometheus metrics on /metrics; one JSON model.call audit line per served call.
  8. StandaloneA hard design rule: the gateway needs no other AIR service at runtime, in any environment.

2 · Components

The modules under src/air_model_gateway/ and how a request moves through themCode
  1. Thin edgeMiddleware bounds the request id and counts requests; routes only authenticate and hand over to api/v1/model_calls.py, so the two model routes can't drift apart.
  2. Composition rootmain.py::create_app builds every collaborator once and hangs it on app.state. Outside local it refuses to start without its config files and tokens.
  3. Control planePolicy grants (fail closed outside local) and per-service token buckets.
  4. The call pathmodel_calls chooses the chain (catalog), checks the cache and the budget, runs the router, then prices, records spend, stores the cache entry and writes the audit line.
  5. RouterRuns a chain; it never decides which models. Adapters turn every failure into a ProviderError. Cloud SDKs load lazily.
  6. Per-service cacheKeyed on the calling service, the chain and every field that changes the question. Refusals and cut-off answers are never cached.
  7. Degrade, never failAll Redis access goes through RedisStore; each user falls back to memory. /v1/ready reports Redis but never gates on it.

3 · Request flow

POST /v1/generate, step by step, with every early exitRuntime

Before the model (steps 1–7)

Everything cheap and local runs first: identity, grant, rate, choice, cache, budget. A request refused here costs no provider call. Validation errors (unknown field, bad role, out-of-range temperature) are 422 and never reach a provider.

The model (step 8)

The router walks the chain the catalog chose: per-attempt deadline, open breakers and spent provider quotas skipped, one jittered retry if a failure was transient. It returns 429 only if every rung was throttled; otherwise 502 naming each rung's error.

After the model (step 9)

Price from pricing.yaml (local models are free), add to the service's daily spend, store in the cache, count tokens and cost, write one model.call line: service, operation, choice, provider, model, tokens, cost, cached, finish_reason.

4 · Model choice

Callers choose a class; deploy/routing.yaml decides the modelsRouting
  1. The requestmodel defaults to auto. provider is a preference, not a filter. pin names an exact model and stands alone.
  2. Grant firstThe policy says which classes, providers, embedding models and pins a service may use; outside the grant is 403.
  3. Cataloggateway/models.py turns an allowed choice into a chain. A choice that means nothing (unpublished name, provider not in the class) is 422.
  4. Classeslocal stays on our servers; cloud uses cloud models only; auto is local first with cloud fallback.
  5. OverridesA class can mean something different for one service; tuning one consumer never moves another. /v1/capabilities shows each service its own chains.
  6. EmbeddingsA name is permanent: one model, fixed dimensions, never a fallback. A new model is a new name (-v2) and a re-index.
  7. PreferenceMoves the provider's rungs to the front and keeps the rest as fallback. The cache key includes the chain, so a routing change invalidates old answers.

5 · Resilience

Failover, retries and circuit breakers in gateway/router.pyRouting
  1. Breaker checkAn open breaker skips the rung without a call, so a dead model costs nothing while it is down.
  2. Provider quotaprovider_quotas caps calls per minute to a provider across all services; over quota, the rung is skipped and the chain fails over.
  3. DeadlineEach attempt has its own deadline (60 s). A caller bounds the whole call with its own client timeout.
  4. Retryable?Timeouts, 429, 5xx and dropped connections are transient; a 400 or a refusal is not, and is never retried.
  5. One retry layerThe router retries the whole chain once with jittered backoff. SDK retries are off so retries never multiply.
  6. BreakerPer (provider, model), per replica. Five consecutive transient failures open it; a trial call after 30 s closes or reopens it.

6 · Streaming

stream: true on /v1/generate answers with Server-Sent EventsRuntime
  1. Before the first tokenEverything can still fail as plain HTTP (401, 403, 422, 429, 502), and the router can still fail over to the next rung.
  2. After itStatus is 200 and the model is fixed. Events: one start, many delta, then done or error.
  3. doneThe same summary as a JSON answer without content: id, model, provider, usage, cost, finish_reason.
  4. errorA Problem body (code, detail, request id). The answer so far is incomplete; retry the whole call if needed.
  5. DisconnectThe gateway closes the provider stream. The call is audited as client_disconnected and not billed to the budget (usage is unknown).

On the wire

event: start
data: {"id":"…","model":"llama3.2:3b","provider":"ollama","cached":false}

event: delta
data: {"content":"Hel"}

event: done
data: {"id":"…","usage":{…},"cost_usd":0.0,"finish_reason":"stop",…}

Headers Cache-Control: no-cache and X-Accel-Buffering: no keep proxies from buffering. A cache hit replays as one delta. Clients read with a read timeout above the 30 s idle limit, not a total timeout. EventSource can't POST: use fetch and read the body.

Errors (application/problem+json)

Status · codeMeaning · action
401 unauthorizedMissing or unknown token
403 policy_deniedNot granted (operation, class, provider, pin, embedding model)
422 validation_errorBody invalid; detail names each field
422 invalid_model_choiceChoice means nothing here; see capabilities
429 rate_limitedRetry with backoff
429 budget_exceededStop until Retry-After (next UTC day)

finish_reason

9 · GKE deployment

Staging and production on GCP: in-cluster onlyDevOps
  1. ConsumersPods in the listed namespaces only; the NetworkPolicy refuses everyone else.
  2. ServiceClusterIP. No Ingress and no public load balancer.
  3. DeploymentHardened pods, HPA, PDB, zone spread; preStop plus a grace period lets in-flight calls finish.
  4. ConfigRouting, pricing and policy passed with --set-file; a change rolls the pods without a new image.
  5. SecretsSecret Manager mounted by the GKE add-on (CSI) as files in SECRETS_DIR; nothing secret in Kubernetes or GitHub.
  6. Model serversRun in their own namespace, owned separately; the gateway only gets their URLs from values.
  7. Secret ManagerConsumer tokens, provider keys, Redis URL and CA. deploy/gke/bootstrap-secrets.sh loads and rotates them.
  8. MemorystoreShared cache, rate limits and spend across pods, with AUTH and TLS on a private IP.

10 · Delivery pipeline

From a commit to production, and the one-time setup per environmentDevOps
  1. CI = make verifyThe same gates run on a laptop and in CI, so a green laptop predicts a green build.
  2. Build onceOne image per release, pushed to staging's registry and tested there.
  3. Human approvalThe prod GitHub environment requires a reviewer; promotion copies the exact digest staging tested.
  4. TerraformMemorystore, secrets and IAM, Workload Identity; optionally the VPC, NAT, Autopilot cluster and registry.
  5. TokensOne per consumer, issued into Secret Manager. Rotation is two-phase (--rotate, then --retire-old) with no downtime.

11 · Environments and gates

Where it runs, and the command that proves each oneAssurance

make verify

Lint, mypy strict, tests with a 90% coverage floor, OpenAPI drift, lock freshness, dependency audit, shellcheck, hadolint, chart and Terraform validation. Exactly what CI runs.

Runtime gates

integration-test and kind-test make real calls per grant: 401 for an unknown token, 200/403 per grant, pins, embedding names, streaming, readiness, Redis, and (kind) the NetworkPolicy block. gke-smoke runs the same checks inside GKE after each deploy.

Settings

Prefix AIR_MODEL_GATEWAY_, __ for nesting (AIR_MODEL_GATEWAY_OLLAMA__BASE_URL). Env beats SECRETS_DIR files beats .env. .env.example documents every key.

Design principles

StandaloneNo other AIR service at runtime.
Classes, not modelsCallers state intent; the owner picks models.
Config, not codeModels, prices and grants change without a release.
Fail closedOutside local, nothing is allowed unless granted.
Degrade, never failRedis is optional; every user falls back.
One retry layerThe router; SDK retries are off.
StatelessNo conversations kept; callers own history.
One contractdocs/openapi.json, checked against the code.
